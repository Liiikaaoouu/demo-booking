# Бронирование переговорных

## Задание

### Правила

- Можно использовать любые ИИ-инструменты: чат-ассистенты, агенты в IDE, CLI-агенты. Это не снижает оценку, но и не повышает её: мы оцениваем результат и то, как вы проверяете код, в том числе сгенерированный. Работать без ИИ тоже нормально.
- Стек: PHP 8.4, Laravel 13, PostgreSQL.
- Коммитьте по ходу работы: по истории мы смотрим, как развивалось решение. Оцениваем осмысленность коммитов, а не их количество.
- На следующем этапе вы объясните решение и внесёте в него небольшое изменение во время звонка. Код, который вы не можете объяснить, считается невыполненным.

### Задача

В компании два офиса: Москва (Europe/Moscow) и Новосибирск (Asia/Novosibirsk), в каждом есть переговорные. Предыдущий разработчик написал API бронирования, и пользователи жалуются на ошибки. Код — в `app/Http/Controllers/BookingController.php`.

### Часть 1. Ревью

Составьте `REVIEW.md`: перечислите проблемы, для каждой — серьёзность (critical / major / minor) и как исправить. Если место выглядит подозрительно, но проблемой не является, — тоже напишите об этом.

### Часть 2. Доработка

Исправьте `store` и `destroy` так, чтобы выполнялись правила:

- Брони одной комнаты не пересекаются. Встречи «впритык» разрешены: 10:00–11:00 и 11:00–12:00 — это не пересечение.
- Длительность от 15 минут до 4 часов, шаг 15 минут (10:00, 10:15…).
- Бронь целиком укладывается в рабочее время 09:00–20:00 по местному времени офиса, где находится комната. Клиент присылает время в ISO 8601 с любым смещением.
- Отменить бронь может только её автор.
- Понятные ошибки валидации (422).
- Других ограничений на даты нет.
- Feature-тесты на все правила выше.

Можно менять модели и миграции и добавлять свои классы. Методы `index` и `today` исправлять не нужно, их достаточно разобрать в ревью.

Бонус: при двух одновременных запросах на один слот может создаться двойная бронь. В основной части достаточно, чтобы брони не пересекались при последовательных запросах. Гонку исправьте или опишите в README, как бы вы это сделали.

## Запуск

Нужны Docker и Docker Compose.

```sh
docker compose up -d --wait
docker compose exec app php artisan migrate:fresh --seed
```

Первый запуск занимает несколько минут: контейнер устанавливает зависимости. API доступно по адресу `http://localhost:8000/api`.

В контейнере PHP 8.4. Если открываете проект в IDE, выставьте языковой уровень
PHP 8.3 или выше: в `BookingScheduler` есть типизированные константы
(`const int`), они появились только в 8.3, и IDE на 8.2 подсветит их как ошибку.

## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "user_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Лог созданных броней пишется в `storage/logs/bookings.log`.

## Решение

`store` и `destroy` переписаны; `index` и `today` намеренно не трогала — их
разбор в `REVIEW.md`. Почему сделано именно так, что отброшено и какие у
решений компромиссы — в `DECISIONS.md`.

- `app/Http/Requests/StoreBookingRequest.php` — формат запроса: `room_id`,
  `title`, `starts_at`, `ends_at` (ISO 8601 с любым смещением). Ошибки — 422 с
  ключами полей.
- `app/Services/BookingScheduler.php` — правила: длительность 15 минут – 4 часа,
  шаг 15 минут, окно 09:00–20:00 по времени офиса комнаты, пересечения, гонка.
- Время нормализуется в UTC и хранится в `timestamptz`. Часовой пояс офиса
  применяется только там, где важно местное время: рабочие часы и сетка.
- Автор брони всегда берётся из токена, `user_id` убран из `fillable`.
- `destroy` проверяет автора и отдаёт 403; route-model binding — 404 на
  несуществующую бронь.
- `bookings` получила индекс `(room_id, starts_at, ends_at)`.

### Пересечения и гонка

Пересечение проверяется строгими сравнениями: `starts_at < $конец` и
`ends_at > $начало`. Поэтому 10:00–11:00 и 11:00–12:00 не конфликтуют.

Гонку закрывает не приложение, а база:

```sql
EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)
```

Два одновременных запроса могут оба пройти проверку в коде, но второй `INSERT`
упрётся в ограничение (SQLSTATE `23P01`), и `BookingScheduler` вернёт 422.
Нужно расширение `btree_gist` — миграция `2026_11_10_000001_harden_bookings_table`
его создаёт, поэтому пользователю БД нужны права на `CREATE EXTENSION` (на проде
его обычно ставит DBA заранее). Схема меняется отдельной миграцией, а не правкой
исходной: там, где база уже развёрнута, `create_bookings_table` повторно не
выполнится.

Если в таблице уже есть пересекающиеся брони (старый код это позволял),
миграция упадёт на добавлении ограничения — такие записи нужно разрешить до
выката, автоматически решать за бизнес, какую встречу отменить, нельзя.

Почему не `SELECT ... FOR UPDATE`: блокировка строки комнаты работает, только
пока все пишут через этот код, помнят про транзакцию и не обходят её сидером
или импортом. Ограничение в схеме действует всегда.

### Что покрыто тестами

43 feature-теста: правила и их границы (15 минут, 4 часа, 09:00, 20:00,
встречи впритык), часовые пояса Москвы и Новосибирска, строгая проверка формата
ISO 8601 (любое смещение, `Z`, отказ для времени без смещения и несуществующих
дат), отсутствие лишних ограничений на даты, права на отмену, 401/403/404/422, и
отдельно — что ограничение в базе не даёт записать пересечение в обход сервиса.

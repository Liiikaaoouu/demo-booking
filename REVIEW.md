# Ревью: API бронирования переговорных

Разбирала `BookingController` и всё, что вокруг: модели, миграции, роуты, конфиг.
Задача сформулирована как «пользователи жалуются на ошибки», поэтому приоритет —
то, что приводит к неверным данным, дырам в доступе и падениям, а не стиль.

**Коротко:** 5 critical — SQL-инъекция, подмена автора брони, удаление чужой
брони, потеря часового пояса при записи, рабочие часы в поясе клиента вместо
офиса. 9 major — нет валидации, встречи впритык считаются конфликтом, нет
ограничений длительности и сетки, «сегодня» в UTC, N+1, нет индекса, гонка,
500 вместо 401 без `Accept`. 10 minor. Дальше — по пунктам, с пометкой, что
воспроизведено запуском.

Как проверяла: подняла окружение из `docker compose`, развернула копию исходного
кода (`upstream/master`) на отдельной базе и прогнала сценарии через `curl`,
заглядывая в `bookings` через `psql`. Всё, что помечено **[воспроизведено]**,
наблюдала своими глазами: коды ответов, текст ошибок, значения в колонках.
Остальное — чтение кода и понимание, как ведут себя Laravel и PostgreSQL.

Обозначения: **critical** — дыра в безопасности или порча данных; **major** —
неверное поведение по требованиям; **minor** — качество, поддержка, мелочи.

## Critical

### C1. SQL-инъекция в `store` **[воспроизведено]**

```php
$conflict = DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");
```

Три пользовательских значения склеены в SQL строкой, и `room_id` даже не
приводится к целому. Что это даёт на практике **[воспроизведено]**:

- `room_id=abc` — 500, и в тело ответа (при `APP_DEBUG=true`) уезжает весь
  запрос плюс координаты базы: `Connection: pgsql, Host: postgres, Port: 5432,
  Database: legacy`. Для внутреннего API это ещё и утечка инфраструктуры.
- Текст запроса полностью управляется клиентом. Результат `DB::select` здесь
  используется только как флаг «есть пересечение», поэтому вытащить данные
  напрямую через этот запрос нельзя — но это везение конкретной строки кода, а
  не свойство решения: любая правка (например, добавить `id` в ответ) превратит
  это в полноценный data leak, а сейчас уже позволяет ломать проверку и вешать
  базу тяжёлым подзапросом.

**Как исправить:** никакого сырого SQL с интерполяцией. Либо query builder с
биндингами (`where('starts_at', '<', $end)`), либо `DB::select($sql, [$a, $b])`.
Приведение типов — на входе, через валидацию (`integer` + `exists:rooms,id`).

### C2. Автор брони приходит от клиента **[воспроизведено]**

```php
$booking = Booking::create($request->all());
```

В `Booking::#[Fillable]` есть `user_id`, поэтому `user_id` из тела запроса
спокойно записывается в базу. Любой авторизованный пользователь создаёт бронь
от чужого имени, и она появляется в чужом `GET /api/bookings`.

**Как исправить:** автора брать только из токена — `$request->user()->bookings()->create(...)`,
а `user_id` убрать из `fillable`. Тогда даже при случайной передаче поля оно
ни на что не влияет: в модели его просто нет в списке заполняемых.

### C3. Любой может отменить чужую бронь **[воспроизведено]**

```php
public function destroy($id)
{
    Booking::findOrFail($id)->delete();
```

Авторизации нет вообще: `auth:sanctum` подтверждает, что пользователь
аутентифицирован, но не что он владелец записи. Требование «отменить может
только автор» не выполнено.

**Как исправить:** route-model binding (`/bookings/{booking}`) + сравнение
`$booking->user_id` с `$request->user()->id`, иначе 403. Для Laravel-пути
аккуратнее Policy (`BookingPolicy::delete`), но для одной проверки достаточно
явной.

### C4. Время хранится «настенным», а не как момент **[воспроизведено]**

Колонка `timestamp` (без зоны), `APP_TIMEZONE=UTC`, а в модель приходит
`Carbon` с offset клиента. Laravel форматирует дату в её собственном часовом
поясе (`Y-m-d H:i:s`, без смещения), поэтому `10:00+03:00` ложится в базу как
`10:00`, а не как `07:00 UTC`.

Последствия **[воспроизведено]**:

- `2026-12-01T10:00:00+03:00` — это 07:00 UTC, а в колонке лежит
  `2026-12-01 10:00:00`.
- Запрос на `2026-12-01T10:00:00+00:00` (13:00 по Москве, другое реальное время)
  получает 409 «Комната занята» — потому что оба запроса схлопнулись в одну
  настенную отметку `10:00`.

То есть один и тот же момент в разных смещениях даёт две несвязанные записи, а
разные моменты — ложный конфликт. Сортировка и «сегодня» считаются по третьей
шкале.

**Как исправить:** нормализовать в UTC до сохранения
(`CarbonImmutable::parse($v)->utc()`) и хранить в `timestamptz`, чтобы
PostgreSQL тоже не терял зону. Проверка: `2026-12-01T10:00:00+03:00` в ответе
и в БД — `2026-12-01T07:00:00Z`.

### C5. Рабочие часы считаются в поясе клиента, а не офиса **[воспроизведено]**

```php
$start = Carbon::parse($request->starts_at);
if ($start->hour < 9 || $start->hour >= 20) {
```

`$start->hour` — это час в том смещении, которое прислал клиент. Для
новосибирской комнаты (UTC+7) клиент честно присылает `02:00+00:00` = `09:00`
местного — и получает 422 «Нерабочее время». А `09:00+03:00` для московской
комнаты пройдёт проверку, хотя это нормально; но `09:00+07:00` для московской —
это 05:00 по Москве, и он тоже пройдёт, потому что «час» равен 9.

**Как исправить:** перевести оба конца брони в `office->timezone` и проверять
локальное время. Нужен `$room->office` — то есть комната должна быть загружена
(и это ещё один аргумент против `$request->room_id` в сыром виде).

Дополнительно: проверяется только начало. `19:00–23:00` проходит как валидная
бронь, хотя рабочий день кончается в 20:00.

## Major

### M1. Нет валидации входа → 500 вместо 422 **[воспроизведено]**

Ни одного `validate()`. Что реально происходит **[воспроизведено]**:

- пустое тело → 500, `SQLSTATE[42601] syntax error at or near "AND"` (в запрос
  подставились пустые строки);
- нет `title` → 500, `SQLSTATE[23502] null value in column "title" violates
  not-null constraint` с полным текстом SQL;
- `starts_at: "tomorrow at ten"` → 500, `SQLSTATE[22007] invalid input syntax
  for type timestamp` — строка уходит в SQL как есть;
- несуществующая комната → 500, `SQLSTATE[23503] foreign key violation`.

Требование «понятные ошибки валидации (422)» не выполнено ни в одном месте.

**Как исправить:** `FormRequest` с правилами на формат (`required`, `integer`,
`exists`, `date`, `after`) и отдельный слой бизнес-правил, который бросает
`ValidationException` с внятными сообщениями и ключами полей.

### M2. Пересечение считается нестрого — встречи «впритык» конфликтуют **[воспроизведено]**

```php
AND starts_at <= '{$request->ends_at}'
AND ends_at >= '{$request->starts_at}'
```

При `10:00–11:00` и `11:00–12:00` второе условие даёт `11:00 <= 11:00` —
истина, бронь отклоняется с 409. По требованиям это разные встречи.

Правильная формула пересечения полуинтервалов: `starts_at < $end AND ends_at > $start`.

**Как исправить:** заменить `<=`/`>=` на `<`/`>` и вынести это в scope модели,
чтобы формула была в одном месте.

### M3. Нет ограничений на длительность и шаг сетки

Требуются 15 минут – 4 часа и кратность 15 минутам. Сейчас можно забронировать
`10:00–10:00` (нулевая длительность, если пройдёт курсор), сутки и `10:07`.

**Как исправить:** считать разницу в минутах и проверять оба конца на сетку —
в часовом поясе офиса, а не в UTC (для этих офисов разницы нет, но правило
должно быть корректным по определению).

### M4. Нет проверки `ends_at > starts_at`

`ends_at` раньше `starts_at` даёт отрицательный интервал, который проваливает
любые проверки длительности только если они есть. Сейчас — просто записывается
в базу.

**Как исправить:** правило `after:starts_at` на уровне запроса.

### M5. `today()` собирает «сегодня» в UTC, а не в поясе офиса

```php
->whereDate('starts_at', today())
```

`today()` — это полночь UTC приложения. Для Новосибирска (UTC+7) с 00:00 до
07:00 местного времени эндпоинт отдаёт вчерашние брони, а вечерние — завтрашние.
Плюс `whereDate` превращает `starts_at` в дату средствами БД, что убивает
индексные возможности.

**Как исправить:** взять «сегодня» в `office->timezone`, построить
`[начало дня, начало следующего дня)` в UTC и фильтровать по диапазону
(`where('starts_at', '>=', $from)->where('starts_at', '<', $to)`).

### M6. N+1 в `today()`

```php
->get()->map(fn ($b) => ['author' => $b->user->name])
```

На каждую бронь — отдельный `SELECT` пользователя. Для пяти комнат терпимо,
для комнаты с плотным днём — десятки запросов на вызов.

**Как исправить:** `->with('user')` до `get()`.

### M7. Нет индекса под проверку пересечений

`bookings` имеет только PK и FK-индексы. Запрос «есть ли пересечение по
комнате» сканирует всю таблицу. На демо-данных незаметно, на тысячах броней —
заметно.

**Как исправить:** составной индекс `(room_id, starts_at, ends_at)`. Само
условие пересечения по `ends_at` индекс использует частично, но отсечение по
комнате и нижней границе работает.

### M8. Гонка двух запросов создаёт двойную бронь (бонусное задание)

`SELECT` на конфликт и `INSERT` не атомарны и не в транзакции: два параллельных
запроса на один слот оба видят «свободно» и оба пишут.

Варианты:

1. `SELECT ... FOR UPDATE` по строке комнаты внутри транзакции — сериализует
   запросы на одну комнату, но требует явной транзакции и пессимистичной блокировки.
2. **Exclusion constraint** — база сама запрещает пересечение:
   `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)`
   (нужно расширение `btree_gist`). Плюс: работает и для чужих путей записи —
   сидеров, импортов, будущих воркеров. Минус: нужно ловить `23P01` и отдавать 422.
3. Advisory lock по `room_id` — то же, что (1), но без строки в БД.

Реализовано (2): ограничение в миграции + перехват `QueryException` с SQLSTATE
`23P01` в сервисе. Почему не (1): блокировка строки комнаты работает, только
пока все пишут через это приложение и не забыли про транзакцию — ограничение в
базе не забыть.

### M9. Без `Accept: application/json` неаутентифицированный запрос даёт 500 **[воспроизведено]**

Это зафиксировано в README как известное поведение, но это баг, а не фича.
`AuthenticationException` без ожидания JSON уходит в `redirect()->guest(route('login'))`,
маршрута `login` нет — отсюда ответ:

```json
{"message": "Route [login] not defined.", "exception": "Symfony\\Component\\Routing\\Exception\\RouteNotFoundException", ...}
```

Для API это ещё и утечка внутренностей.

**Как исправить:** в `bootstrap/app.php` явно отдавать 401 для `api/*`:

```php
$exceptions->render(function (AuthenticationException $e, Request $request) {
    if ($request->is('api/*')) {
        return response()->json(['message' => 'Unauthenticated.'], 401);
    }
});
```

## Minor

- **M-1. `index` возвращает модель как есть.** Наружу уезжают `user_id`,
  `room_id`, служебные поля. Для внутреннего API терпимо, но `BookingResource`
  зафиксировал бы контракт. Как исправить: `BookingResource::collection(...)`.
- **M-2. `orderByRaw('starts_at DESC')`.** Инъекции нет (литерал), но сырой SQL
  там, где хватает `latest('starts_at')`. Мелочь, которая приучает не замечать
  `Raw`.
- **M-3. Формат ошибок не единый.** Конфликт отдаётся как `{"error": "..."}`, а
  всё, что прошло через валидатор, — как `{"message": ..., "errors": {...}}`.
  Клиенту придётся разбирать два формата; лучше один. Как исправить: отдавать
  конфликт через `ValidationException`, чтобы ответ собирал один обработчик.
- **M-4. `Log::withContext()` меняет контекст логгера до конца запроса.** Для
  одного вызова безвредно, но следующий лог в этом же запросе получит чужой
  `booking_id`. Правильнее передавать контекст вторым аргументом
  `Log::channel('bookings')->info('Booking created', ['booking_id' => $id])`.
- **M-5. Конфликт отдаётся 409, а требования просят 422.** По HTTP 409 для
  конфликта состояния корректен, но задание явно говорит «понятные ошибки
  валидации (422)», а клиенту проще обрабатывать один класс ошибок. Сделала 422,
  но отмечу: если бы контракт был свободным, 409 был бы аккуратнее.
- **M-6. `destroy($id)` без route-model binding и без типа.** `findOrFail` даёт 404, это ок, но
  route-model binding читается лучше и убирает лишний запрос.
- **M-7. `today()` форматирует время через `__toString`.** `$b->starts_at . ' – '`
  даёт `2026-12-01 07:00:00` в UTC — ни офисного времени, ни ISO 8601. Как
  исправить: перевести в пояс офиса и отдавать `format('H:i')` или `toIso8601String()`.
- **M-8. `title` без ограничения длины.** Колонка `varchar(255)`, всё длиннее —
  500 вместо 422. Как исправить: правило `max:255`.
- **M-9. Отмена — физическое удаление.** Для «отменить бронь» это допустимо, но
  история встреч теряется. Если брони нужны для отчётности — `softDeletes`.
- **M-10. Первый `docker compose up -d --wait` падает с `unhealthy`.** В
  `compose.yaml` у `app` стоит `start_period: 300s`, а первый запуск делает
  `composer install` внутри контейнера и не укладывается в пять минут — `--wait`
  успевает отдать ошибку, хотя приложение поднимается через полминуты после
  этого. Лечится `start_period` побольше или вынесением `composer install` в
  сборочный слой Dockerfile. Исправлено: `start_period` поднят до 900s — иначе
  документированные в README две команды запуска не проходят на чистой машине.

## Выглядит подозрительно, но проблемой не является

- **`DB::select` как таковой.** Сырой SQL в Laravel — нормальный инструмент,
  проблема этого места — интерполяция (C1), а не сам вызов.
- **`return $booking;` отвечает 201, а не 200.** В коде нет явного статуса, и
  это выглядит как «создание отдаёт 200». На самом деле Laravel ставит 201 для
  только что созданной модели (`wasRecentlyCreated`). Проверил `curl`-ом — 201.
- **`$request->all()` как таковой.** Mass assignment опасен ровно настолько,
  насколько широк `fillable`. Дыра здесь в `user_id` (C2); если его убрать,
  `$request->all()` перестанет быть дырой (но всё равно не нужен — лишние поля
  молча теряются, и это трудно заметить).
- **`orderByRaw`.** Литеральная строка, параметров нет — инъекции нет.
- **`#[Fillable]` и `#[Hidden]` атрибутами вместо свойств.** Это новое API
  Laravel 13, работает так же, как `protected $fillable`. Стилистически
  непривычно, но не ошибка.
- **Отсутствие `app/Http/Middleware/Authenticate.php`.** В Laravel 11+ middleware
  аутентификации живёт во фреймворке, файл больше не нужен.
- **Тесты на отдельной базе `testing` + `RefreshDatabase`.** База создаётся
  скриптом `docker/create-testing-db.sql` при инициализации тома, рабочую `booking`
  тесты не трогают. Это правильная схема, а не риск.
- **Токены в сидере — литеральные строки.** Для демо это нормально: в базе лежит
  `sha256` от токена, как у обычного Sanctum-токена. В проде так нельзя, но это
  и не прод.
- **`timestamp` без `timestamptz` сам по себе.** Для однoофисного приложения в  одной зоне это рабочая схема; проблема — в связке с C4, где зона теряется.
- **Проверка `exists:rooms,id` отдельным запросом.** Лишний `SELECT`, но
  читаемое сообщение об ошибке важнее одного запроса.
- **Отсутствие транзакции вокруг `store`.** После exclusion constraint она не
  нужна: конфликт ловится базой, остальное — одна вставка.
